# DevBoard 大改修案
# GitHubが苦手な人のための、リポジトリ整理と開発フロー練習ツールへ

作成日: 2026-05-05
対象アプリ: DevBoard
目的:
  GitHubの画面が見づらい、リポジトリが増えると管理しづらい、Issue / Pull Request の使い方が分からない、という課題を解決する。
  現行のMVPカンバンを、非エンジニア・個人開発初心者にとって分かりやすい「リポジトリ整理とGitHub練習ツール」へ育て直す。

注意:
  この計画は、2026年5月5日時点の現行コード調査を前提にしている。
  これは「肥大化した既存機能を隠す改修」ではなく、「MVPカンバンを初心者向けのGitHub練習ツールへ育て直す改修」として扱う。
  現行コードにはTODO、AI実装連携、TagManager、Workspace、Split Panelなどの実装または断片が存在する。
  ただし初心者向けの主導線としては未整理なため、初期MVPでは前面に出さず、既存機能の退避・整理・後続活用対象として扱う。
  MVPから外したが後続で必要な修正・実装は docs/大改修MVP外バックログ.md にまとめる。
  2026年5月時点のReact / Vite / Tailwind / Cloudflare Workers関連の最新バージョンは、実装前に公式情報またはnpmで再確認する。
  実装前チェックコマンド:
    npm outdated
    npm info react version
    npm info react-dom version
    npm info vite version
    npm info @vitejs/plugin-react version
    npm info tailwindcss version
    npm info typescript version
    npm info vitest version
    npm info eslint version
    npm info @typescript-eslint/eslint-plugin version

================================================================================
1. 背景
================================================================================

DevBoardの元々の着想は以下。

  - GitHubの公式サイトは、非エンジニアや初心者には情報量が多くて見づらい。
  - 自分が作ったリポジトリが増えてくると、何がどの状態なのか分かりにくくなる。
  - リポジトリをカンバン形式で見やすく整理できる場所がほしい。

現行実装でできていることは以下。

  - 4列カンバン
  - リポジトリ検索
  - 並び替え
  - 保存ビュー
  - 保存プリセット
  - 列名変更
  - 列内/列間の並び替え
  - 手動列割り当て
  - リポジトリ非表示
  - 手動リポジトリ追加
  - 最近のIssue / Pull Request表示

一方で、現行の主画面は「リポジトリを理解する画面」というより、カンバン操作や保存設定が前に出ている。
GitHubに慣れていない人にとっては、各リポジトリの目的、今の状態、次にやることを把握しにくい。

なお、以下は現行コードに実装または断片が存在するが、初心者向けの主導線としては未整理である。
今回の初期MVPでは「新規追加候補」ではなく「既存機能を前面に出さない整理対象」として扱う。

  - TODO / Issue同期関連の型、保存、画面
  - AI実装連携、AI実行履歴、GitHub Actions連携
  - TagManager / TagSelector
  - Workspace / Split Panel
  - GitHub Issue / Pull Request一覧表示
  - グリッド / リスト / カンバン切替

今回の大改修では、機能を増やすのではなく、以下を主軸に再設計する。

  1. リポジトリ管理をもう一度シンプルにする。
  2. GitHub用語を初心者向けに翻訳する。
  3. Issue / Pull Request の練習ができるようにする。
  4. 既存MVP機能は必要に応じて奥に置く。
  5. DevBoardを「GitHubの代替UI」ではなく「GitHubに慣れるための日本語レイヤー」にする。

2. 新コンセプト
================================================================================

新しいDevBoardのコンセプト:

  DevBoardは、GitHubが苦手な人のための
  リポジトリ整理と開発フロー練習ツール。

もう少し詳しく言うと:

  DevBoardは、GitHubに慣れていない個人開発者や非エンジニアが、
  自分のリポジトリを分かりやすく整理しながら、
  Issue・Pull Request・ブランチ・マージといった開発フローを
  少しずつ練習できる日本語ダッシュボード。

キャッチコピー案:

  GitHubを、こわくなくする。
  リポジトリ整理から、Issue・Pull Requestの練習まで。

または:

  作ったものを整理して、開発の流れを少しずつ覚える。
  GitHub初心者のための開発ボード。

3. 対象ユーザー
================================================================================

主な対象:

  - GitHubの画面が見づらいと感じる人
  - 個人開発を始めたばかりの人
  - リポジトリが増えて管理できなくなってきた人
  - Issueを作ったことがない人
  - Pull Requestを作るタイミングが分からない人
  - ブランチやマージの流れがまだイメージできない人
  - AIでコードは作れるが、開発管理の作法がまだ分からない人
  - 非エンジニアだが、GitHubを使って制作物を管理したい人

対象外、または優先度を下げるユーザー:

  - すでにGitHub Projects / Linear / Jira / Notion / ZenHubを高度に使いこなしているチーム
  - 複雑なチーム開発ワークフローを求める企業
  - CI/CDや監査ログを重視するエンタープライズ用途

DevBoardは、まず個人開発初心者・非エンジニア・GitHub苦手層に振り切る。

4. 設計方針
================================================================================

4.1 原則

  - 最初の画面では、リポジトリ管理以外を見せすぎない。
  - GitHub用語は、必ず日本語の意味とセットで表示する。
  - Issue / Pull Request は、いきなり本番連携させず、練習モードを用意する。
  - 機能は「初心者向け」「練習用」「上級者向け」に分ける。
  - AI機能は強力だが、初期画面では前面に出しすぎない。
  - カスタマイズよりも、迷わない導線を優先する。
  - クリックしたらGitHubへ飛ぶだけのカードではなく、DevBoard内で理解できる詳細画面を作る。
  - データを増やすより、状態を分かりやすく翻訳する。
  - 言葉をやさしくする。
  - 画面を減らす。

4.2 やらないこと

  - Jiraのような本格的なタスク管理ツールを目指さない。
  - GitHub Projectsを完全再現しない。
  - 最初からIssue / PR / Actions / AI / Tagsを全部見せない。
  - ダッシュボードを数字だらけにしない。
  - 非エンジニアに英語のGitHub用語だけを投げない。
  - 複雑なワークフロー自動化を最初の改修で入れない。

  - TODOボード側にはdnd-kit利用箇所がある。

現状の特徴:

  - Vite + React + TypeScript のシンプルなSPA構成。
  - Cloudflare Pages Functionsで認証とGitHub APIプロキシを実装。
  - フロント側に多くのUI状態管理がある。
  - localStorageにactiveTab、保存ビュー、プリセット、列設定、非表示リポジトリ、テーマなどが保存されている。
  - Repo / ViewPreset / RecentItem / Todo / AIExecutionHistory の型が存在する。
  - 現行タブは board / activity / manual の3つ。
  - 旧 updates / todos は activeTab 移行で activity に寄せる実装がある。
  - 最近のIssue / Pull Request表示、Issue作成クライアント、TODO、AI実装連携の実装断片は存在する。
  - ただし、初心者向けの学習導線としては未整理で、初期画面に出すには情報量とリスクが大きい。
  - 課題は「Activity中心」ではなく、「カンバン操作中心で、リポジトリの目的や次の行動が見えにくい」こと。

6. 技術ブラッシュアップ方針
================================================================================

6.1 React

現状:
  React 18系

候補:
  React 19系へのアップデートを検討する。

ただし:
  実装前にReact 19系の最新安定版、React DOM、Testing Library、Vite pluginとの互換性を確認する。
  React 19へ上げる場合、型やStrictMode、ref、use周り、テスト挙動に影響が出る可能性があるため段階的に行う。

方針:
  大改修の初期PRではReact 18系のまま進める。
  UI構造の整理を先に行い、React 19系への更新は別PRに分ける。
  理由:
    UI再設計とメジャーアップデートを同時にやると、問題の切り分けが難しくなるため。

6.2 Vite

現状:
  Vite 5系

候補:
  Vite 8系、または2026年時点の最新安定版へ更新を検討。

方針:
  実装前に以下を確認:
    - Node.jsの推奨バージョン
    - Cloudflare Pagesのビルド環境との相性
    - @vitejs/plugin-reactの対応バージョン
    - Vitestとの互換性
    - Tailwindとの互換性

  Vite更新はUI改修と分離して行う。

6.3 Tailwind CSS

現状:
  Tailwind CSS 3系

候補:
  Tailwind CSS 4系へのアップデートを検討。

ただし:
  Tailwind 4系は設定方式やビルドまわりが変わる可能性があるため、既存のtailwind.config.js、CSS変数、PostCSS構成への影響を確認する。

方針:
  今回の大改修では、まずTailwind 3.4のままデザイントークンを整理する。
  その後、別フェーズでTailwind 4移行を検証する。
  理由:
    現在のDevBoardはCSS変数とTailwind拡張が多く、同時移行するとUI崩れが大きくなる可能性がある。

6.4 TypeScript

現状:
  TypeScript 5系

候補:
  2026年時点の最新安定版へアップデート検討。

方針:
  TypeScriptは比較的上げやすいが、現状では npx tsc --noEmit が通らない。
  まずtypecheck用scriptを追加し、既存の型エラーを直してからアップデートを検討する。
  先に以下を整える:
    - Repo型
    - Practice型
    - AppMode型
    - TabType
    - LocalStorage schema

6.5 ESLint

現状:
  ESLint 8系

候補:
  ESLint 10系、または2026年時点の最新安定版へ移行検討。

注意:
  ESLint 9以降ではFlat Config移行が必要になる可能性がある。
  現状のnpm run lintはエラーではなくreact-refresh/only-export-components警告が残る状態。
  初期PRでは、必要に応じて警告の扱いを整理しつつ、ESLintメジャー移行は分離する。

方針:
  最初に現行ESLint 8系のままlintを通す。
  ESLintメジャー移行はUI改修後の別PRとして扱う。

6.6 アニメーション

現状:
  framer-motionは現行package.jsonの直接依存として存在し、TabNavigation、RepoCard、RepoGrid、RepoColumnなどで使われている。
  Tailwindのtransition / hover / transformも併用されている。

方針:
  初期改修では新しいアニメーションライブラリを追加しない。
  詳細パネルや練習ステップの表示も、まずはCSS transitionで十分にする。
  framer-motionの利用範囲を初期MVPで広げない。

6.7 ドラッグ&ドロップ

現状:
  @dnd-kit/core / sortable / utilities は現行package.jsonの直接依存として存在する。
  RepoBoardの列内/列間移動はHTML5 Drag and Dropで実装されている。
  TodoBoard側にはdnd-kit利用箇所がある。

方針:
  初心者向けの最初の画面ではドラッグ&ドロップを前面に出さない。
  既存カンバンのHTML5 DnDは残してもよいが、初期導線からは控えめにする。
  シンプルモードでは、状態変更はセレクトやボタンで行えるようにする。
  dnd-kitの新規導入や利用拡大は初期改修では行わない。

6.8 Cloudflare Workers / Pages

現状:
  OAuth、セッション、GitHub APIプロキシをCloudflare Functionsで実装。

方針:
  バックエンド構成は維持する。
  今回の大改修の主眼はUX整理なので、Cloudflare構成の大きな変更は避ける。
  ただし、Issue作成やPR練習モード用にAPIを整理する。

追加検討:
  - GitHub Issue作成API
  - GitHub Issue一覧取得API
  - GitHub Pull Request一覧取得API

ただし最初はlocalStorageベースで練習モードを作り、本番GitHub連携は後段にする。

8. モード設計
================================================================================

ユーザーレベルを3段階に分ける。

  1. Simple Mode
     - 初心者向け
     - リポジトリ整理が中心
     - Issue / PR用語は補足表示のみ
     - AIや高度なActivityは隠す

  2. Practice Mode
     - Issue / PR / ブランチ / マージを練習
     - GitHubにはまだ反映しない
     - DevBoard内で疑似的に流れを体験

  3. Advanced Mode
     - 実際のGitHub Issue作成
     - Pull Request確認
     - Activity表示
     - AI実装連携
     - タグ管理
     - 列管理
     - 保存プリセット

型案:

  export type UserMode = 'simple' | 'practice' | 'advanced';

  export type FeatureVisibility = {
    showActivity: boolean;
    showAutomation: boolean;
    showColumnSettings: boolean;
    showTagManager: boolean;
    showPresets: boolean;
    showGithubSync: boolean;
    showAiActions: boolean;
  };

初期実装での扱い:

  - UserMode / FeatureVisibility は、最初から実装しない。
  - まずはタブ、リポジトリ詳細、練習ドラフトだけで成立させる。
  - Advanced Mode は将来の置き場として設計に残すが、初回PRの実装対象にしない。
  - 設定画面を作る段階で、必要なら userMode を localStorage に保存する。

9. 用語の翻訳方針
================================================================================

GitHub用語はそのまま出さず、初心者向け日本語とセットで表示する。

  Repository:
    表示名: リポジトリ
    補足: 作ったアプリやコードを入れておく場所

  Issue:
    表示名: やることカード
    補足: GitHubではIssueと呼びます。修正したいこと、作りたい機能、困っていることをメモする場所です。

  Pull Request:
    表示名: 変更の確認リクエスト
    補足: GitHubではPull Requestと呼びます。作業した変更を確認して、取り込むための場所です。

  Branch:
    表示名: 作業用の分岐
    補足: 本体を壊さずに、別の場所で作業するためのコピーのようなものです。

  Merge:
    表示名: 変更を取り込む
    補足: 作業用の分岐で行った変更を、本体に反映することです。

  Commit:
    表示名: 変更の記録
    補足: どんな変更をしたかを保存する記録です。

  Push:
    表示名: GitHubに送る
    補足: 自分のPCで行った変更をGitHubに反映することです。

  Clone:
    表示名: 自分のPCにコピーする
    補足: GitHub上のリポジトリを自分のPCに持ってくることです。

UIでは以下のように表示する。

  やることカード
  GitHubでいう Issue です

  変更の確認リクエスト
  GitHubでいう Pull Request です

  作業用の分岐
  GitHubでいう Branch です

10. リポジトリ管理画面の再設計
================================================================================

10.1 目的

最初の画面で以下が分かるようにする。

  - 自分が何を作っているか
  - どのリポジトリが作業中か
  - どれが放置されているか
  - 次に何をすればいいか
  - GitHubを開かなくても概要が分かる

10.2 新しいリポジトリ状態

旧:
  - Active
  - Stale
  - Dormant
  - Archived

新:
  - 作業中
  - アイデア
  - 見直し中
  - 保留
  - 完了

または自動分類を残す場合:

  - 最近さわった
  - しばらくさわってない
  - かなり放置
  - 完了・終了

推奨:
  自動分類と手動ステータスを分ける。

  自動状態:
    - 最近更新
    - しばらく未更新
    - 長期未更新
    - アーカイブ済み

  自分の状態:
    - 作業中
    - アイデア
    - 見直し中
    - 保留
    - 完了

型案:

  export type RepoAutoHealth =
    | 'recent'
    | 'stale'
    | 'dormant'
    | 'archived';

  export type RepoUserStatus =
    | 'working'
    | 'idea'
    | 'reviewing'
    | 'paused'
    | 'done';

  export type RepoUserMeta = {
    repoId: string;
    status: RepoUserStatus;
    note?: string;
    nextAction?: string;
    purpose?: string;
    difficulty?: 'easy' | 'normal' | 'hard';
    confidence?: 'low' | 'medium' | 'high';
    updatedAt: string;
  };

10.3 リポジトリ一覧カード

カードに表示する情報:

  - リポジトリ名
  - 説明
  - 何のためのリポジトリか
  - 自分の状態
  - 自動状態
  - 次にやること
  - 最終更新日
  - 言語
  - GitHubで開くボタン
  - 詳細を見るボタン

クリック挙動:

  旧:
    カードクリックでGitHubへ移動

  新:
    カードクリックでDevBoard内の詳細パネルを開く
    GitHubへ移動する場合は明示的に「GitHubで開く」を押す

10.4 表示形式

初期表示:
  リスト表示

理由:
  カンバンは見た目は良いが、初心者にとっては横スクロールやドラッグ操作が分かりづらい。
  最初は1カラムの一覧で、状態・次の行動・メモが見える方が管理しやすい。

切替:
  - リスト
  - カード
  - カンバン

ただし、切替UIは控えめにする。

10.5 検索とフィルター

初心者向けに必要なもの:

  - 名前で検索
  - 状態で絞り込み
  - 最近更新 / 放置で絞り込み
  - 作業中だけ見る

不要または上級者向けに隠すもの:

  - 複雑な保存ビュー
  - 列カスタマイズ
  - 詳細なタグ管理
  - 高度な並び替え

Issueをいきなり「Issue」として扱わない。

表示:

  やることカード
  GitHubでいう Issue です。

12.2 練習フロー

Step 1:
  何をしたいかを書く

  入力例:
    トップページのボタンを見やすくしたい

Step 2:
  なぜやるのかを書く

  入力例:
    初めて見る人に分かりやすくしたいから
    操作に迷わないようにしたいから
    スマホからも使いやすくしたいから

Step 3:
  完了条件を書く

  入力例:
    ボタンの色が目立つ
    説明文が短く分かりやすい
    スマホ幅でも横スクロールしない

Step 4:
  GitHub Issue風に整形する

  生成される形式:

    ## やりたいこと

    ## 完了条件
    - ボタンの色が目立つ
    - 説明文が短く分かりやすい
    - スマホ幅でも横スクロールしない

Step 5:
  保存方法を選ぶ

  - DevBoard内だけに保存する
  - GitHub Issueとして作成する

初期状態では:
  DevBoard内だけに保存する

GitHub作成は:
  明示的に確認してから実行する

13. Pull Request練習モード
================================================================================

13.1 基本方針

Pull Requestは「変更の確認リクエスト」と表現する。

表示:

  変更の確認リクエスト
  GitHubでいう Pull Request です。

13.2 練習フロー

Step 1:
  どのやることカードに対応する変更か選ぶ

Step 2:
  何を変更したかを書く

  入力例:
    ボタンの色を紫に変更した
    説明文を短くした
    スマホ表示の余白を調整した

Step 3:
  確認してほしいことを書く

  入力例:
    ボタンが見やすくなっているか
    文言が分かりやすいか
    スマホで崩れていないか

Step 4:
  PR説明文として整形する

  生成される形式:

    ## 変更内容
    - ボタンの色を紫に変更
    - 説明文を短く調整
    - スマホ表示の余白を修正

    ## 確認してほしいこと
    - ボタンが見やすいか
    - 文言が分かりやすいか
    - スマホで崩れていないか

    ## 関連Issue
    Closes #12

Step 5:
  GitHub PRについて説明する

  ここで以下を説明する:
    - Pull Requestは、変更を本体に取り込む前の確認場所
    - 個人開発でも、作業の記録として使える
    - AIにコードを書かせた場合でも、何を変えたか確認する場所として便利

13.3 本番PR作成について

注意:
  GitHub APIでPRを実際に作るには、ブランチとコミットが必要。
  そのため、初心者向けの最初の実装ではPRそのものの作成は行わない。
  まずはPR説明文を作る練習と、既存PRの読み方に限定する。

将来的に:
  - ブランチ作成
  - ファイル編集
  - コミット
  - PR作成
  まで自動化できるが、これはAdvanced Modeで扱う。

14. TODO機能の位置づけ
================================================================================

現行コードには、Todo型、localStorage保存、TODOボード、ActivityからIssueをTODO化する導線、Workspace内TODOタブなどの実装が存在する。

20. API方針
================================================================================

20.1 今回すぐ必要なAPI

既存のGitHubリポジトリ取得APIは維持。

初回の小分け実装では、新規APIを作らない。
まずはリポジトリ詳細とIssue練習ドラフトをlocalStorageで実装する。

理由:
  - 練習モードはGitHubに反映しないため、APIなしで価値検証できる。
  - GitHub上にデータを作る処理は、誤操作や権限設計の影響が大きい。
  - 既存の /api/github/* にはREST allowlist、GraphQL queryId allowlist、書き込みOriginガード、no-store系ヘッダーがある。
  - ただし本番作成導線を増やす前に、PracticeIssueDraftからのIssue作成に必要な範囲で既存ガードを棚卸しし、不足があれば補強する必要がある。

最初に本番GitHub連携を入れる場合も、対象はGitHub Issue作成だけに絞る。
Issue一覧、Pull Request一覧、Practice API、Repo Notes API、Repo Status APIは後回しにする。

20.2 将来追加するAPI

  functions/api/github/issues/create.ts
  functions/api/github/issues/list.ts
  functions/api/github/pulls/list.ts
  functions/api/github/pulls/detail.ts

追加前に必要な準備:

  - 既存 /api/github/* proxyのpath / method allowlist確認
  - 既存CSRF / Originチェックの確認
  - Cache-Control: no-store の統一確認
  - PracticeIssueDraftからIssue作成する際の専用確認UI
  - OAuth scope確認
  - GitHub上に実データを作る前の確認ダイアログ

20.3 GitHub連携時の注意

Issueを作成する前に必ず確認ダイアログを出す。

確認文:

  GitHubにIssueを作成します。
  この操作はGitHub上に実際のデータを作成します。
  内容を確認してから作成してください。

23.1 リポジトリ画面

見出し:
  あなたのリポジトリ

説明:
  作ったアプリやコードを、目的・状態・次にやることで整理できます。
  GitHubを開かなくても、今どれを進めればいいか分かるようにしましょう。

空状態:
  まだリポジトリが表示されていません。
  GitHubと接続すると、あなたのリポジトリを一覧で確認できます。

次にやること:
  このリポジトリで次にやること

目的:
  このリポジトリは何のため？

メモ:
  自分用メモ

GitHubボタン:
  GitHubで開く

23.2 Issue練習

見出し:
  やることカードを作ってみる

補足:
  GitHubでは、こうした「やること」や「直したいこと」を Issue と呼びます。
  まずはDevBoard内だけで練習してみましょう。

GitHub作成前確認:
  GitHubにIssueを作成します。
  この操作はGitHub上に実際のデータを作成します。
  内容を確認してから作成してください。

23.3 PR練習

見出し:
  変更の確認リクエストを作ってみる

補足:
  GitHubでは Pull Request と呼びます。
  変更した内容を確認して、取り込むための場所です。

23.4 Branch説明

見出し:
  作業用の分岐とは？

説明:
  本体を壊さずに作業するための場所です。
  GitHubでは Branch と呼びます。

23.5 Merge説明

見出し:
  変更を取り込むとは？

説明:
  作業用の分岐で行った変更を、本体に反映することです。
  GitHubでは Merge と呼びます。

27. 最終方針
================================================================================

DevBoardは、高機能なGitHubダッシュボードを目指すのではなく、
GitHubに慣れていない人が、自分の開発物を整理しながら、
GitHubの開発フローを少しずつ身につけられるアプリにする。

今回の大改修で一番大事なのは、巨大な機能追加ではなく育て直し。

  - 小さく進める
  - 迷う導線を減らす
  - 翻訳する
  - 練習できるようにする
  - リポジトリ管理を主役に戻す

この方針で、1PRごとに使える状態を保ちながら進める。
