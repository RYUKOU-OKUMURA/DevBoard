# 大改修MVP外バックログ

作成日: 2026-05-05
対象: DevBoard 大改修
関連: docs/大改修案.md

================================================================================
1. このドキュメントの目的
================================================================================

docs/大改修案.md は、最初に取り組む大改修MVPの計画として扱う。

大改修MVPの中心は以下。

  - リポジトリを1カラムで分かりやすく見る
  - GitHubへ勝手に飛ばず、DevBoard内で詳細を見る
  - リポジトリごとに目的、メモ、次にやること、自分の状態を保存する
  - Issueを「やることカード」として練習し、DevBoard内にドラフト保存する
  - lint / typecheck / test / build の最低限の開発基盤を直す

このファイルでは、最初のMVPからは外すが、後続で必要になる修正・実装を整理する。

================================================================================
2. 優先度の考え方
================================================================================

P0:
  MVP後すぐ、またはGitHub上に実データを作る前に必要。

P1:
  MVPの利用感を見た後、継続利用に必要になりやすい。

P2:
  将来価値はあるが、MVP検証前に入れるとスコープが膨らむ。

================================================================================
3. P0: MVP後すぐ必要になりやすいもの
================================================================================

3.1 GitHub API proxyの棚卸しと補強

必要性:
  GitHub Issue作成など、GitHub上に実データを作る前に必要。
  現行の /api/github/* にはREST allowlist、GraphQL queryId allowlist、書き込みOriginガード、no-store系ヘッダーがある。
  ただしPracticeIssueDraftからGitHub Issueを作る導線を追加する前に、既存ガードで十分か棚卸しし、不足があれば補強する。

やること:
  - 既存path / method allowlistの対象を確認する
  - PracticeIssueDraftから必要になるGitHub APIだけが通ることを確認する
  - POST / PATCH / DELETE系のOriginガードが期待通り効くことを確認する
  - Cache-Control: no-storeが認証系/API系レスポンスで統一されているか確認する
  - GitHub APIエラーを日本語UIで扱いやすい形に整形する

MVPから外す理由:
  MVPはlocalStorage中心で、GitHubへ書き込まないため。

着手条件:
  GitHub Issue作成を入れる前。

-------------------------------------------------------------------------------

3.2 GitHub Issue作成

必要性:
  練習したIssueドラフトを、実際のGitHub Issueへ変換できると学習から実践へ進める。

やること:
  - 既存のIssue作成クライアントまたは既存proxy経由で、PracticeIssueDraftからGitHub Issueを作成する
  - 作成前に必ず確認ダイアログを出す
  - 作成後にgithubIssueNumber / githubIssueUrl / syncStatusを保存する
  - 失敗時に分かりやすい日本語エラーを出す

MVPから外す理由:
  初回は「練習して保存する」だけで価値を確認できる。
  GitHubに実データを作る処理は安全設計が必要。

着手条件:
  Issue練習ドラフトが使える状態になり、既存proxyの棚卸しと不足補強が終わった後。

-------------------------------------------------------------------------------

3.3 localStorageスキーマとアカウントスコープの整理

必要性:
  RepoUserMetaやPracticeIssueDraftを保存し始めると、アカウント切り替え時の衝突や古いデータの扱いが問題になりやすい。
  保存keyのアカウントスコープと不正データ耐性は、MVP中に最低限決めておく必要がある。

やること:
  - RepoUserMetaの保存keyをアカウント単位にする
  - PracticeIssueDraftの保存keyをアカウント単位にする
  - 既存の保存ビュー、プリセット、列設定、非表示リポジトリとの関係を整理する
  - schemaVersionを持たせるか検討する
  - localStorageの不正データを安全に無視・復旧できるようにする

MVP内で最低限やること:
  - 保存keyのアカウントスコープ
  - localStorageの不正データで画面を壊さないガード

MVP後に回すこと:
  - schemaVersionを使った本格的な移行処理
  - 既存保存データ全体の棚卸しと統合

着手条件:
  RepoUserMeta / PracticeIssueDraftの保存仕様が固まった時点。

-------------------------------------------------------------------------------

3.4 localStorage / presetStorage / 新規storage群の責務整理

必要性:
  現行では src/utils/storage.ts を共通localStorageヘルパーとして使い、src/utils/presetStorage.ts が保存プリセットを扱っている。
  大改修で repositoryMetaStorage / practiceStorage を追加すると、保存責務やキー命名が散らばりやすい。
  大改修でstorage層を増やす前に、混乱を減らしたい。

やること:
  - src/utils/storage.ts を共通ヘルパーとして扱う方針を明確にする
  - presetStorage / repositoryMetaStorage / practiceStorage の責務を分ける
  - 保存keyの命名規則とアカウントスコープ規則を揃える
  - 必要なテストを追加する
  - 既存localStorageデータを壊さない

MVPから外す理由:
  リポジトリ詳細とIssue練習の価値検証そのものには直接関係しない。

着手条件:
  repositoryMetaStorage / practiceStorage を追加する前後。

-------------------------------------------------------------------------------

3.5 セキュリティ・設定まわりの小修正

必要性:
  GitHub書き込み機能を入れる前に、認証・環境変数・Cookie周りの不整合を減らす。

やること:
  - SESSION_SECRET / ENCRYPTION_KEY の長さ検証
  - /api/auth/status のreadiness判定にSESSION_SECRETを含める
  - PUBLIC_ORIGINの扱いを login / status / callback で揃える
  - 認証系レスポンスのCache-Controlを確認する

MVPから外す理由:
  MVPはGitHub書き込みをしない前提なら、最初のUI価値検証をブロックしない。

着手条件:
  GitHub Issue作成または本番公開前。

================================================================================
4. P1: 継続利用のために必要になりやすいもの
================================================================================

4.1 Pull Request練習

必要性:
  Issueを作れるようになった後、変更内容と確認観点を整理する練習が必要になる。

やること:
  - PullRequestPracticeDraftを保存する
  - 変更内容、確認してほしいこと、関連Issueを入力する
  - PR説明文Markdownを生成する
  - Branch / Mergeの説明を短く添える

MVPから外す理由:
  まずIssue練習が成立するかを確認したい。
  実PR作成はブランチとコミットが必要で重い。

着手条件:
  Issue練習ドラフトが自然に使われるようになった後。

-------------------------------------------------------------------------------

4.2 独立した「やること」画面

必要性:
  リポジトリ詳細の「次にやること」やIssueドラフトが増えると、横断的に見たいニーズが出る。

やること:
  - 今日やる
  - 次にやる
  - 作業中
  - 終わった
  - Issueドラフトとの関係を整理する
  - GitHub Issue化は明示アクションにする

MVPから外す理由:
  初回から独立タブにすると、Issue練習やRepoUserMetaと役割が被りやすい。

着手条件:
  「リポジトリごとの次にやること」だけでは足りないと分かった後。

-------------------------------------------------------------------------------

4.3 設定 / Advancedの置き場

必要性:
  保存ビュー、プリセット、列管理、既存カンバン、最近の更新などを初心者向け主導線から外す置き場が必要になる。

やること:
  - 設定画面を追加する
  - カンバン表示への導線を奥に置く
  - 保存ビュー / プリセット管理を設定内へ移す
  - 最近の更新を「詳しく見る」扱いにする
  - 将来のAdvanced Modeの入口だけ作る

MVPから外す理由:
  初回は「リポジトリを理解する」体験を先に作る。
  設定画面を先に作ると、画面構成がまた重くなる。

着手条件:
  RepositoryHome / DetailPanel / Issue練習が固まった後。

-------------------------------------------------------------------------------

4.4 ランディングページ刷新

必要性:
  プロダクトの訴求を「GitHub初心者向け」に合わせる必要がある。

やること:
  - コピーを新コンセプトに変更する
  - AIや高度な自動化を前面に出しすぎない
  - GitHubログイン前に、何ができるか分かるようにする

MVPから外す理由:
  まずログイン後の主体験を固める方が重要。

着手条件:
  リポジトリ整理とIssue練習の画面が見せられる品質になった後。

-------------------------------------------------------------------------------

4.5 データのエクスポート / リセット

必要性:
  localStorage中心で運用する場合、ユーザーがメモや練習ドラフトを退避・削除できる導線があると安心。

やること:
  - RepoUserMetaのエクスポート
  - PracticeIssueDraftのエクスポート
  - アカウント単位のリセット
  - 破壊操作前の確認

MVPから外す理由:
  初期データ量では必須ではない。

着手条件:
  保存データが増え、リセットや移行ニーズが出た後。

================================================================================
5. P2: 将来価値はあるが急がないもの
================================================================================

5.1 GitHub Issue一覧 / Pull Request一覧

必要性:
  実際のGitHub上のIssue / PRを読めると、練習と実践の橋渡しになる。

やること:
  - リポジトリごとのIssue一覧
  - リポジトリごとのPull Request一覧
  - Open / Closed / Mergedの日本語表示
  - 既存IssueとPracticeIssueDraftの紐付け

MVPから外す理由:
  読み取りAPIが増えると画面と状態管理が重くなる。
  まずは自分で作る練習を優先する。

-------------------------------------------------------------------------------

5.2 クラウド同期

必要性:
  複数端末で使う場合、localStorageだけではRepoUserMetaや練習ドラフトが共有されない。

候補:
  - Cloudflare KV
  - Cloudflare D1

MVPから外す理由:
  個人用MVPではlocalStorageで十分に価値検証できる。

着手条件:
  複数端末利用やデータ消失対策が重要になった後。

-------------------------------------------------------------------------------

5.3 依存関係メジャーアップデート

必要性:
  React / Vite / Tailwind / ESLint などは将来的に上げる必要がある。
  npm auditでVite/esbuild、Rollup、PostCSS周辺の指摘も出ている。

やること:
  - 非破壊で直せるaudit修正
  - Vite更新
  - Vitest更新
  - React 19更新
  - Tailwind 4更新
  - ESLint Flat Config移行

MVPから外す理由:
  UI再設計と依存メジャー更新を同時に行うと、問題の切り分けが難しい。

着手条件:
  MVPの主要画面が安定した後。

-------------------------------------------------------------------------------

5.4 共通UIコンポーネント整備

必要性:
  Button / Card / Badge / Dialog / Stepper などは、画面が増えると共通化したくなる。

MVPから外す理由:
  最初から共通化すると抽象が先行しやすい。
  2〜3回重複してから切り出した方が安全。

着手条件:
  RepositoryHome、DetailPanel、PracticeHomeで同じUIが繰り返し出てきた後。

-------------------------------------------------------------------------------

5.5 AI実装連携

必要性:
  将来的には、Issueを元にAIへ実装を依頼する導線は強い特徴になり得る。
  現行コードにはAICommandTab、AI実行履歴、GitHub Actions連携フック、TODOからAI実装を呼ぶ導線の実装断片がある。

やること:
  - Advanced Mode内に置く
  - 既存実装を棚卸しし、再利用・退避・削除の判断をする
  - 実行前に何が起きるか説明する
  - GitHub上に変更が作られる可能性を明示する
  - Issue / PRの流れを理解したユーザー向けにする

MVPから外す理由:
  初心者にIssue / PRの理解より先にAI実行を見せると、学習導線が崩れる。
  既存実装はあるが、初心者向けMVPの価値検証には不要で、現時点で前面に出すと誤操作リスクが高い。

-------------------------------------------------------------------------------

5.6 Workspace / Split Panel / TagManager / GitHub Actions詳細

必要性:
  高度な管理用途では役立つ可能性がある。
  現行コードにはWorkspace、SplitPanel、TagManager、Issue / PR / TODO / AI系のWorkspaceタブが存在する。

MVPから外す理由:
  既存実装はあるが、初心者向けの最初の体験では情報量が多すぎる。
  初心者向けのリポジトリ整理とGitHub練習には必須ではない。

扱い:
  明確な利用シーンが出るまで主導線に置かない。
  後続でAdvanced / 設定 / 詳しく見る導線へ退避するか、再利用できないものは削除を検討する。

================================================================================
6. 実装順の目安
================================================================================

MVP完了後の推奨順:

  1. GitHub API proxyの棚卸しと補強
  2. localStorageスキーマと保存実装の整理
  3. GitHub Issue作成
  4. PR練習
  5. 設定 / Advancedの置き場
  6. 独立した「やること」画面
  7. ランディングページ刷新
  8. 依存関係メジャーアップデート
  9. GitHub Issue / PR一覧
  10. クラウド同期
  11. AI実装連携の再整理

この順番は固定ではない。
MVPを使ってみて、実際に足りないものから前倒しする。

================================================================================
7. 判断基準
================================================================================

後続項目を実装するかどうかは、以下で判断する。

  - 初心者がGitHubの流れを理解しやすくなるか
  - リポジトリ管理が毎日使いやすくなるか
  - GitHub上に実データを作る場合、安全性と確認導線が十分か
  - UIがまた複雑にならないか
  - 既存MVPの価値を壊さないか

この基準に合わないものは、便利そうでも急がない。
