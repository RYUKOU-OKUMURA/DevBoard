# コードレビュー（2025-10-23）

本ドキュメントは GitHub_Dashboard プロジェクトの現状コードに対するレビュー結果です。改善提案と、今回セッション内で実施した最小限のリファクタリング内容を記載します。

## サマリー
- 良い点
  - 型定義（src/types）が整理されており、Repo や表示に必要な型が簡潔。
  - 分類・検索・整列などの関心ごとが utils や lib に分離されており見通しが良い。
  - コンポーネント分割（RepoBoard/RepoColumn/RepoCard 等）の方向性が適切で、Tailwind によるスタイルも一貫している。
- 改善余地
  - 分類ロジックが utils/classify.ts と lib/classifyRepo.ts に重複実装されている。
  - クリック可能なカードのアクセシビリティ（キーボード操作、role/aria）が不足していた。
  - window.open の安全な利用（noopener/noreferrer）はされているが、ブロック時のフォールバックがない。
  - 未使用の props が存在（RepoCard の columnKey）し、呼び出し側との結合が不要に強くなっていた。

## 詳細レビュー

### 1. 構成・モジュール境界
- utils と lib に近い責務のユーティリティが重複。特に classifyRepo が 2 箇所（src/utils/classify.ts と src/lib/classifyRepo.ts）に別実装として存在。
  - それぞれの API 仕様が少し異なる（utils 側は AppConfig、lib 側は ClassifyOptions と now 指定、境界値の扱いなど）。
  - 仕様差異のまま統合すると既存テストの破壊リスクがあるため、段階的統合（片方を薄いアダプタにし、振る舞い差異をテストで担保）が望ましい。
  - 現段階では利用箇所の影響が読みにくいため、本セッションではロジック統合は見送り、重複点の指摘のみ行いました。

提案:
- まず使用箇所を洗い出し、単一のソース（例: src/lib/classifyRepo.ts）へ集約。
- もう一方（utils/classify.ts）は re-export か Adapter に変更し、仕様差異（閾値の inclusive/exclusive、日数切り上げ/切り捨て等）を明文化。
- 共通の date ユーティリティ（日数計算、未来日扱い）を utils/date.ts として切り出し、両者から参照する。

### 2. アクセシビリティ（A11y）
- RepoCard は div に onClick を持たせていたが、キーボード操作（Enter/Space）に対応していなかった。スクリーンリーダー配慮の role と aria-label も未設定。

対応（本セッションで実施）:
- RepoCard に role="button" / tabIndex=0 / onKeyDown(Enter/Space) / aria-label を追加。

### 3. 安全な外部リンク処理
- window.open の戻り値が null の場合（ポップアップブロック等）のフォールバックがない。

対応（本セッションで実施）:
- utils/openExternal.ts を追加し、window.open 失敗時は同タブ遷移へフォールバック。例外時も同様にフォールバック。
- RepoCard は openExternal を利用。

### 4. 型の厳密化・不要コードの削除
- RepoCard の props に columnKey が存在するが、内部では未使用。呼び出し側（RepoColumn）から余計な props 受け渡しが発生。

対応（本セッションで実施）:
- RepoCard から columnKey を削除し、RepoColumn 側の呼び出しも修正。
- これにより結合度が下がり、コンポーネントの責務が明確化。

### 5. 命名・可読性
- 現時点で大きな命名の問題は見当たらないが、date 計算や threshold 常数値などの共通定数は utils/date.ts などに寄せると見通しが上がる。

提案:
- MS_PER_DAY、differenceInDays のようなロジックは共通化し、テスト対象にする。
- timeAgo や formatDate のロケール/単位表現は i18n 対応を見据え、ラッパを用意すると柔軟性が増す。

### 6. テスト
- lib と utils の両方にテストが存在（__tests__ ディレクトリ複数）。重複実装のままだとテストコストも二重化しやすい。

提案:
- 分類ロジックの単一起点に対し、ユニットテストを集約。差分仕様がある場合は Adapter 層のテストとして分離。
- search/sort の境界ケース（空配列、null/undefined フィールド、極端な日付等）を増やす。

### 7. パフォーマンス
- 現状規模では重大な問題は見えないが、Repo 数が数百〜数千になると検索・並び替え・分類を都度全量再計算する構造はコスト増。

提案:
- メモ化（useMemo）や Web Worker の導入を検討。検索入力中はデバウンスをかける。
- グリッド仮想化（react-window 等）で大量カードの描画コストを削減。

### 8. セキュリティ
- フロントエンドでの token 取り扱い説明は README にあり、プロキシ案も提示済み。実装側では、API レイヤの fetch 時にヘッダへ token を乗せる箇所での露出・ログ出力等に注意が必要。

提案:
- 本番ビルド時の source map 制御、開発ツールでの token ログ抑止。
- CORS/Rate Limit を考慮したプロキシ構成の雛形を docs に追加。
